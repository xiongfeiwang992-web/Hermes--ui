## 1.4 原版是什么（背景）

原「未来家」客户端多为 **Electron 壳 + 云端鼎尖 ERP**：

| 层 | 是什么 | 功能在哪 |
|----|--------|----------|
| A. 桌面壳 | 未来家.exe / dj-browser | 许可、指纹、多标签、下载更新、快捷键、本机能力 |
| B. 云端 ERP | dingjianerp 网页 | 盘客/交易/财务/人事/新房/办公/营销…主体业务 |
| C. 多端配套 | 小程序 / 网站 / 微站 / APP | 与 ERP 同一账号与数据 |

自研目标是：**做自己的系统**，分期交付；第一期通常只做「能开店用的主路径」，但**沟通阶段必须先把原版能做的能力写全、勾清楚**，避免后期反复返工。

## 1.5 分期标记说明（全文通用）

> **重要（与开发对齐）**  
> 1. 四个选项是**上线批次建议**，不是「能不能写软件」。绝大多数原版可借鉴功能**都能自研开发**。  
> 2. **本文已按建议结论预填勾选**（每组四选一打 `[x]`），方便开发排期与对照；业务方仍可改勾。  
> 3. **可自研**的功能默认进入 **MVP / P2 / P3**，不标「暂不做」。  
> 4. **「暂不做」尽量少**：仅留给厂商许可/破解相关、明显违法风险、或明确本期不碰的危险运维项。外部依赖未签约时勾 **P3** 并备注「需外部服务」，而不是大面积暂不做。  
> 5. 分期只表示建议上线批次，**不是「做不了」**。

| 标记 | 含义 |
|------|------|
| **MVP必须** | 第一期必做，主路径或门店开业刚需（能跑门店主营） |
| **P2** | 二期建议，主路径跑通后加深，完整门店能力 |
| **P3后期** | 后期批次；成本高、非刚需、或需外部签约（仍可开发/预留接口） |
| **暂不做或替代方案** | 极少数：不宜做或用替代方案（如本地账号替代云许可；不做厂商许可模块） |
| **禁** | 红线，永不做（厂商许可仿造、指纹云校验、破解等） |

第三编细项与第二编模块建议已预填一致；争议可改勾并写「待定：原因」。签字区见 3.Q（预填建议待业主确认签字）。

## 2.1 主路径锚点（所有讨论的锚点）

```text
录盘 → 录客 → 跟进 → 带看 → 成交提交 → 店长/老板审批 → 收款 → 提成可见
```

成功标准（沟通时应认可或改写）：

1. 管理员建门店与经纪人账号  
2. 经纪人 A 录 1 套房、1 个私客  
3. 写跟进并创建带看（关联该房该客）  
4. 有意向后建成交单并获审批  
5. 登记佣金收款并算出提成  
6. 经纪人 B 看不到 A 的私客；店长看本店

## 2.2 模块 M00 · 工作台 / 主控台

### 模块说明（原版做什么）

原版登录后进入主控台/工作台：公司信息、服务开通状态、组织/员工/许可/考勤快捷入口、预警消息（服务到期前消息+短信）、待办汇总。桌面壳另有多标签承载各业务页。

### 功能点清单

| 编号 | 功能点 | 说明 |
|------|--------|------|
| M00-01 | 工作台首页 | 今日待跟进、逾期跟进、待审批成交、待收款摘要 |
| M00-02 | 快捷入口 | 新建房源/客源/带看/成交 |
| M00-03 | 预警区 | 服务到期、存储/短信余额类（原版有；自研可改「数据备份提醒」） |
| M00-04 | 角色差异首页 | 经纪人看本人待办；店长看本店；财务看待收款；管理员看全公司 |
| M00-05 | 主控台公司信息 | 公司名、门店数、员工数只读卡片 |
| M00-06 | 页面设置 | 水印、列表密度、工具箱（原版有电脑/手机端模板） |

### 建议分期
- [x] MVP必须：M00-01、M00-02、M00-04（简版）  
- [x] P2：M00-05（主控台公司信息只读卡片）  
- [ ] P2：M00-06（页面设置细项若仍有缺口）  
- [ ] P3后期：原版级服务/余额预警（若有 SaaS 化）

# 第五编 · MVP 需求规格（草案 · 待勾选对齐后定稿）

> 以下为推荐的第一期规格摘要。若第三编勾选与此冲突，**以勾选为准改规格**。  
> 字段级完整表见分册 `MVP需求规格.md`。

## 5.1 角色与权限矩阵

| 能力 | 管理员 | 店长 | 经纪人 | 财务 |
|------|:------:|:----:|:------:|:----:|
| 管理门店/员工 | ✅ | ❌ | ❌ | ❌ |
| 看本店房源 | ✅全公司 | ✅本店 | ✅本店公开+本人盘 | ❌ |
| 新建/编辑房源 | ✅ | ✅本店 | ✅本人接盘 | ❌ |
| 改接盘人 | ✅ | ✅本店 | ❌ | ❌ |
| 看私客 | ✅ | ✅本店 | ✅本人 | ❌ |
| 看公客 | ✅ | ✅本店 | ✅本店 | ❌ |
| 写跟进/带看 | ✅ | ✅ | ✅本人相关 | ❌ |
| 提交成交 | ✅ | ✅ | ✅ | ❌ |
| 审批成交 | ✅ | ✅本店 | ❌ | ❌ |
| 登记收款 | ✅ | 仅查看 | ❌ | ✅ |
| 看提成 | ✅ | ✅本店 | ✅本人 | ✅ |

**保密盘**：`is_private=true` 时仅接盘人、店长、管理员可见（若第四编改为「店长不可见」则改矩阵）。

## 5.2 组织

- 实体：公司 → 门店 → 员工（一人一店）  
- 能力：门店增改启停；员工增改、角色、重置密码、启停；禁用不可登  
- 员工只停用不物理删；MVP 不建「区域」层  

## 5.3 房源（HOUSE）

**关键字段**：售/租、状态、小区（手填）、价格（售万元/租元月）、面积、业主姓名电话、登记人、接盘人、保密盘、来源备注。  

**状态机**：

```text
draft → available ⇄ suspended → deal_pending → closed
任意非 closed → withdrawn（撤盘）
closed / withdrawn 终态
```

**能力**：列表筛选；新建编辑详情；改状态记日志；店长改接盘人；电话按权限脱敏；详情看跟进/带看/成交时间线。

## 5.4 客源（CUS）

**关键字段**：姓名电话、买/租、预算、等级 A/B/C、私客/公客、状态、维护人。  

**状态**：`new → following → viewing → deal_pending → closed`；另有 `invalid`、转公客池。  

**规则**：新建默认私客；经纪人见本人私客+本店公客；转公/认领；手机号查重软提示；**MVP 不做自动掉公**（除非第四编勾了）。

## 5.5 跟进（FLW）

内容、方式（电话/微信/拜访等）、下次跟进时间；挂在房或客上；详情可新增；待跟进列表（今日/逾期）建议 P0/P1。

## 5.6 带看（VIEW）

关联 1 客 + 1 房 + 时间 + 主看人 + 可选陪看；结果：`pending/interested/considering/rejected/deal`；完成前须非 pending；可从有意向带看发起成交。

## 5.7 成交 / 收款 / 提成（DEAL）

**成交单**：草稿→提交→通过/驳回；驳回原因必填；通过后房客置已成交并生成提成。  
**佣金**：应收合计；建议支持业主佣+客户佣且合计相等；多经纪人 `split` 合计 100%。  
**收款**：财务对已审批单登记；未收=应收−已收；可允许超收预警。  
**意向金**：可选；held→冲抵。  
**提成**：`应提总额 = 应收佣金 × 经纪人池比例`；再按分成比例拆到人；经纪人看本人、店长看本店。

## 5.8 明确不做 / 后期项（与第三编预填对齐）

| 类别 | 项 |
|------|-----|
| **禁 / 暂不做** | 厂商许可与指纹云校验、DNS elevate / jsc 热更仿造、全国楼盘库采购或破解、厂商人脸签照搬、违法爬取网签 |
| **非 MVP（见 P2/P3，仍可开发）** | 地图找房、视频全景、钥匙/实勘、新房报备线、财务总账、CA 电子签（需外部）、真隐号（需外部·接口预留）、外网群发（需合规）、积分分红、租赁托管全流程等——以第三编勾选批次为准，**不等于做不了** |

# 第六编 · 架构与实现原则（进入开发后遵循）

> 本章是**设计约束**，不是「已经上线」的宣告。实现形态（桌面/Web）以勾选为准。细稿见 `软件设计方案-架构UI交互功能.md`。

## 6.1 分层原则

```text
界面层 → 统一 API 客户端 → 传输适配（IPC 或 HTTP）
       → 权限单点 → 领域服务（状态机/规则）→ 仓储 → 数据库
```

| 原则 | 含义 |
|------|------|
| 业务进领域层 | 页面与壳不写提成/审批真相 |
| 传输可换 | 先桌面 IPC 或先 Web，领域层不变 |
| 服务端强制 | 隐藏按钮≠安全 |
| 事件解耦 | 成交审批通过后，房客状态由订阅更新，禁止乱改他表 |
| 枚举英文、界面中文 | 库 `available`，界面「在售」 |
| 可测试 | 关键规则有自动化或清单验收 |
| 离线优先（若选桌面） | 本地库起步；多端协同再上服务端 |

## 6.2 建议技术方向（可再议）

| 项 | 建议 | 备选 |
|----|------|------|
| 客户端 | 桌面壳 + 本地库，或浏览器 + 服务 | 按门店是否多终端决定 |
| 数据 | SQLite 起步；多店多端再 PostgreSQL | |
| 权限 | 角色 + 门店范围 + 本人数据 | |
| 部署 | 单机离线优先；需要协同再上服务端 | |

## 6.3 UI / 交互要点（开发期）

- 信息架构按 2.0 菜单树分组，避免侧栏无序堆砌  
- 列表：筛选 + 空态 + 错误提示；带看/成交用下拉选房客，禁止只靠手输 ID  
- 危险操作（驳回/作废/撤盘）原因必填  
- 金额：售价按万、佣金按元（可千分位）——与第四编口味一致时再定  

## 6.4 主路径验收清单（开发完成后点）

- [ ] 四角色账号可登录且权限不串  
- [ ] 录盘录客跟进带看成交收款提成跑通  
- [ ] 私客/保密盘/跨店隔离抽查通过  
- [ ] 驳回无原因不可提交；审批后房客状态正确  
- [ ] 关键操作有审计日志
